# 自動制作の入力書式・ルール

2026-10-15に自動制作を実装。入力済み台本をDots用パイプへ送ると、既存台本のコピーから音声・画像生成、MP4、投稿用テキストまで自動実行する。CodexからDots仕様のパイプで通し試験に成功した。起動・命令・完了判定は [実装状況](実装状況.md) と [機械読取ルール](パイプ仕様.json) を参照する。

ユーザーは [台本入力.txt](書式/台本入力.txt) をコピーして入力する。Dotsはこのnote.mdと入力された台本を読み、制作指示を解釈する。現在のパイプ操作は [本編の通信仕様](../制作支援/パイプ/Dots連携.md) を参照する。

## 台本・シーンの書式

- 既存台本のコピーから制作する。入力中・編集中の台本はコピー元の候補から除外する。
- コピー元の新しさは、保存済み台本の更新日時を基準にする。漫画とアニメで候補を分け、それぞれの最新台本を選ぶ。現在は漫画のみでも、この分類ルールを最初から適用する。該当種類の候補がない場合に、別の種類へ勝手に切り替えたり新規作成したりしない。
- Dotsは`app-auto-sources`で一覧と除外理由を取得し、一覧の`projectId`を`app-auto-source-check`へ渡して個別台本を確認できる。`eligible`は候補可否、`selected`は同種類で最新の自動選択対象、`copyValidated`はGUIと同じコピー処理のメモリ上検証成功を表す。検査では保存しない。`copyValidated=true`だけでは入力中の除外条件を解除せず、制作設定の充足やMP4完成も意味しない。
- 元台本は保持し、新しい作品IDへコピーする。採用したコピー元のID・種類・更新日時を作業記録に残す。
- レイアウト・VOICEVOX設定・説明キャラと配置は、利用者がGUIのコピー後に「次へ」を進めて再利用できている実動作を基準に引き継ぐ。古い仕様書の記述だけを理由に初期化・破棄しない。実装時にはGUI経路とパイプ経路の結果を照合する。
- 作品名を入力し、種類は「アニメ／漫画」の不要な方を消して一方を残す。ニコニコ漫画の作品URLは任意で記入でき、指定された場合は作品特定に利用する。
- 行頭の `*シーン名` で通常シーンを開始する。`画像：` は画像生成の指示、`表示：` は画像下の補助テキスト。`本文：` から次のブロックまでを読み上げセリフとし、途中の改行を保持する。
- `*背景` は共通背景専用。`画像：` の指示で生成し、通常シーン・読み上げ本文には含めない。
- サムネイルは既存の自動生成を継続し、入力欄を設けない。説明キャラは選択した実キャラファイルから正しく参照画像を用意し、名称だけで外見を推測させない。
- 自動化では画像の目視確認を待たず採用する方針。破損等の機械的検査は残す。自動制作ジョブでは検査後に自動採用・保存する。

## 音声・セリフ・字幕

- VOICEVOXによる読み間違いやイントネーションの違いは許容する。これらの確認・調整のために自動制作を停止したり、人間の確認を待ったりしない。
- セリフ本文と字幕は同じ内容にする。入力書式の `本文：` に書いたセリフを音声合成と字幕の共通の元データとし、字幕だけを要約・言い換え・省略しない。通常シーンと総評の両方に適用する。
- コピー元の異なる字幕・読み指定は新しい本文へそのまま流用せず、新しいセリフと字幕の一致を優先する。本文と異なる音声用表記への書換えを、読み間違い対策として自動で行わない。
- 音声が実際に読み上げた発音を理由に、セリフ本文や字幕を書き換えない。字幕の表示上の折返し・分割は、本文の文字や順序を変えない範囲で行う。
- 通常シーンの `表示：` は画像下の補助テキストであり、セリフ字幕とは別に扱う。読み上げ本文との一致を求める対象には含めない。
- 音声合成の失敗・音声ファイルの欠落等は、許容する読みやイントネーションの違いと区別する。音声生成そのものを省略するルールではない。

## 入力検査・進捗・完了の応答

以下は実装した自動制作の応答ルール。app-auto-startで開始し、app-auto-statusで段階通知と完成ファイルを取得する。app-auto-checkのreadyは事前検査成功だけを意味する。

- 台本データを受け取った時点で入力検査を行う。不足や不正があれば、該当箇所と理由をまとめてパイプの応答へ返す。Dotsはその内容を利用者へ表示する。例は作品名の未記入、種類の両方残し、総評の点数未記入など。任意の作品URLや空欄を許す表示テキストは不足としない。
- 不足時は自動制作を開始しない。勝手に補完して開始せず、修正後の入力を再検査する。
- 全条件を満たす場合も「入力確認完了・制作を開始します」等の受付成功を明示して返す。受付成功を、MP4の完成と混同しない。
- 制作は非同期ジョブとして扱い、同じ作業を追跡するjobIdを返す。Dotsが状態・進捗を取得し、段階ごとの反応を利用者へ表示できるようにする。
- 各段階の開始・完了・失敗を記録する。主な段階は、コピー元の選択・台本コピー、本文と字幕の反映、配役・表情、音声生成、背景・シーン・サムネイル生成と採用、MP4出力、コピペ用テキスト出力。
- 現在のJSONLパイプは要求への応答方式なので、進捗取得で未取得の段階通知をまとめて返す構成を基本とする。各通知に連番を付け、ポーリング間に複数段階が進んでも通知を取りこぼさず、Dotsが同じ通知を繰り返し表示しないようにする。
- MP4の書出しが成功し、成果物ファイルを確認した時点で「MP4完成」を返す。保存先・ファイル名を含める。書出し開始や単なる待機終了を完成としない。
- MP4とコピペ用テキストの両方が出力された時点で、全体完了を返す。MP4が完成してもテキスト出力に失敗した場合は全体成功にせず、完成済みMP4を保持して失敗した段階を報告する。
- 処理中に失敗した場合は、停止した段階・理由・再開可否を返す。自動再試行・再起動後の自動再開は行わず、作成済みファイルと理由を保持して停止する。

## コピペ用テキストの出力

1つのテキストファイルへ、次の順序で出力する。各要素の間は空行で区切る。

```text
<投稿用タイトル>

<概要>

<親作品情報>
```

概要内に必要な改行は保持する。チャプター等の追加項目は今回の対象に含めない。出力先と実際のファイル名は完了応答に含める。

## 実環境での検証

実環境で本編をDotsモード起動し、CodexからDots用パイプを通じたVOICEVOX音声生成・画像生成・MP4・TXT作成が完了した。実際のDotsアクティビティから開始する試験は未実施。リモートDotsからの起動は、そのホストでコマンドを実行できるDots側の機能に依存する。

## 総評は既存の固定5項目

`*総評` は通常シーンと区別する。評価項目は以下の名称・順序で固定し、「要素1」等の仮の名称は使わない。

1. ストーリー
2. キャラクター
3. 作画
4. 演出・テンポ
5. 世界観・設定

各行は `項目名：点数` とする。アニメ・漫画とも、現在のアプリにある同じ固定5項目を採用する。漫画の場合も独断で「作画」を別の項目名へ置き換えない。

点数の標準範囲は **0～5**。小数も入力可能で、小数点は半角 `.` を使う。各項目の点数はチャートへ渡し、評価項目の行を読み上げ本文へ混ぜない。空欄を0点と解釈したり、記入された点数を独断で変更したりしない。コピー元に異なるチャート範囲が設定されている場合の扱いは、今後の仕様で確定する。

`本文：` 以降は総評時のセリフ。総評には画像生成指示を設けず、点数によるチャートを使う。複数行のセリフは既存の総評処理に合わせ、1つの独立した総評チャートシーンとして扱う。

```text
*総評
ストーリー：4
キャラクター：4.5
作画：4
演出・テンポ：3.5
世界観・設定：4
本文：
登場人物の関係が魅力的な作品でした。
今後の展開にも期待したいと思います。
```

### 名称・点数の確認元

- [RigmScriptSummaryModel.pas](../Source/Studio/Model/RigmScriptSummaryModel.pas) の `ScriptSummaryAxisNames` が固定5項目の正本。新規の総評データの範囲はminimum=0 / maximum=5。
- [RigmScriptSummaryFrame.pas](../Source/Shell/Pages/RigmScriptSummaryFrame.pas) のUIも「固定5項目」「初期範囲0～5」としている。
- 保存互換用の検査には旧形式の3～8項目を扱う処理が残るが、自動制作の入力書式へ可変項目数は採用しない。
